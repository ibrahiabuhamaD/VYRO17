# VYRO

تطبيق أولي حقيقي لتجربة مشاركة الفيديو، مبني بـ HTML وCSS وJavaScript Modules، مع خادم Node.js وقاعدة SQLite محلية.

## التشغيل

```powershell
node server.js
```

يحمّل الخادم إعداداته من `1.env`، ثم افتح `http://127.0.0.1:4173` في المتصفح. يتطلب التشغيل Node.js 24 أو إصداراً حديثاً يتضمن `node:sqlite`. لا يحتاج المشروع إلى حزم npm خارجية. لا تضع أسراراً أو كلمات مرور في ملف الإعدادات المحلي.

أمر `npm run build` يفحص صياغة ملفات الخادم والواجهة. التطبيق لا يحتاج مجلد `dist`؛ شغّله عبر `npm start` في منصة تستضيف Node.js.

## النشر على الإنترنت

المشروع خادم Node.js، لذلك GitHub Pages لا يستطيع تشغيله: Pages يستضيف ملفات ثابتة فقط، ولا يشغّل API أو SQLite أو رفع الفيديو. استخدم GitHub كمستودع للمصدر، وانشر التطبيق كخدمة Node على Render باستخدام `render.yaml`:

1. ارفع المستودع إلى GitHub.
2. في Render اختر **New > Blueprint** واربط المستودع.
3. راجع إنشاء خدمة الويب والقرص الدائم `vyro-data` ثم انشر.
4. افتح رابط الخدمة وانتظر نجاح فحص `/api/health`.

إعداد Render يضبط `HOST=0.0.0.0` ويضع قاعدة SQLite والوسائط داخل `/var/data`. القرص الدائم يتطلب خطة Render مدفوعة؛ لا تحذف القرص أو تستبدله بعد بدء الاستخدام، كي لا تفقد بيانات المستخدمين والملفات. عيّن الأسرار من لوحة مزود الاستضافة، ولا تضفها إلى `1.env` أو GitHub.

GitHub Pages يصلح فقط لنسخة واجهة منفصلة لا تعتمد على هذا الخادم، ولن يوفر التسجيل أو النشر الحقيقي بمفرده.

لعرض التصميم وتشغيل الأزرار على GitHub Pages مع خادم منفصل:

1. انشر خدمة Node على Render أولاً، وانتظر نجاح `/api/health`.
2. في Render عيّن `CORS_ORIGINS` إلى أصل Pages كاملاً، مثل `https://USERNAME.github.io`، أو أصل النطاق المخصص، من دون مسار المستودع. لخدمة Render الحالية التي أضيف إليها المتغير `sync: false`، أدخل القيمة من لوحة Render يدوياً.
3. في `public-config.js` ضع عنوان API العام، مثلاً `https://YOUR-API.onrender.com/api`. هذا عنوان عام وليس سراً.
4. من إعدادات المستودع افتح **Settings > Pages** واختر الفرع `main` ومجلد `/(root)`.
5. ارفع التغييرات وانتظر اكتمال نشر Pages، ثم افتح الموقع وتحقق من Network/Console إذا بقي طلب مرفوض.

الواجهة والـAPI على نطاقين مختلفين يحتاجان كوكيز cross-site. بعض المتصفحات أو إعدادات الخصوصية تحظر كوكيز الطرف الثالث؛ الاعتمادية الأفضل تكون بتقديم الواجهة والـAPI تحت نطاق مخصص واحد، أو بنشر الموقع كاملاً على Render من أصل واحد. GitHub Pages وحده لا يشغّل API.

## ما يعمل

- تسجيل الحساب والدخول والخروج بجلسة خادمية وملف كلمة مرور مشتق باستخدام scrypt.
- قاعدة دائمة في `data/vyro.sqlite` للعضويات والمنشورات والمتابعات والإعجابات والتعليقات.
- رفع MP4 أو WebM حتى 50 MB إلى `server/uploads/`، مع فحص ترويسة الملف ودعم HTTP byte ranges.
- موجز عام وFollowing، وعدّادات الملف الشخصي مأخوذة من قاعدة البيانات، وحذف المنشور بواسطة مالكه.
- صلاحيات ظهور المنشور: عام، للمتابعين، أو خاص؛ وتُفحص عند تسليم الوسائط أيضاً.
- بحث عن المستخدمين والمنشورات، مسودات محلية بـ IndexedDB، وPWA shell لا يخزّن استجابات الحساب أو الوسائط.

شغّل `npm run test:smoke` لاختبار التسجيل والنشر والمتابعة والإعجاب والتعليق وتشغيل أجزاء الفيديو والخروج والدخول. ينشئ الاختبار حسابات مؤقتة ويحذفها بعده.
شغّل `npm run test:cors` لاختبار ربط Pages بخادم منفصل، كوكيز الجلسة، ورفض الأصول غير المصرح بها؛ يستخدم الاختبار قاعدة ووسائط مؤقتة ويحذفها بعد الانتهاء.

## الحدود الحالية

هذه نسخة محلية أحادية الخادم، وليست جاهزة للنشر العام. التحقق من البريد واستعادة كلمة المرور و2FA وحدود المعدل ومعالجة/تحويل الفيديو غير مفعلة. الرسائل والقصص والبث الحي ولوحة الإدارة وإعداد أدوار الأدمن غير موصولة بخدمات فعلية؛ لا تظهر بيانات تجريبية لها. قاعدة البيانات والملفات محليتان على الجهاز الذي يشغّل الخادم.

قبل النشر العام، استخدم HTTPS وإدارة أسرار مناسبة، ومحددات معدل، ومراجعة الملفات عبر معالج وسائط، ونسخاً احتياطية، وتخزين كائنات للوسائط، واختبارات أمان. SQLite مناسبة للتطوير المحلي؛ استخدم PostgreSQL عند التوسع إلى عدة خوادم. لا توجد كلمة مرور أدمن مزروعة في الكود؛ أنشئ مسؤولاً عبر bootstrap آمن قبل إضافة أدوات الإدارة.
